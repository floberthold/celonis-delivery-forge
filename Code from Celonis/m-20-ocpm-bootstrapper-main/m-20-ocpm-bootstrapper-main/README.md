## General

This service is based on [fastAPI](https://fastapi.tiangolo.com/) and has the following structure:

```
.
├── app
│   ├── __init__.py
│   ├── main.py
│   └── feature_a
│   │   ├── __init__.py
│   │   └── model.py
│   │   └── service.py
├── tests
│   └── integration
│   │   └── feature_a
│   │   │   └── test_router.py
│   └── unit
│   │   └── feature_a
│   │   │   └── test_router.py
│   │   │   └── test_service.py
```

This structure intends to isolate features into parts that belong to a specific domain.
An advantage of this approach is that it separates work for each layer.
Therefore, the dev team can focus on one layer without affecting another.
Furthermore, they're naturally easier to understand because each of them focuses on its logic.
Another big advantage is that the domain logic is isolated from everything else.
The domain part only contains business logic and can be easily moved to a different environment.
Features that belong to the same domain should be grouped within the domain:

```
.
├── app
│   ├── ...
│   └── domain
│   │   └── feature_a
│   │   │   ├── __init__.py
│   │   │   └── model.py
│   │   │   └── service.py
│   │   └── feature_b
│   │   │   ├── ...
```

## Development

### Setup

Python package and environment management install:

* [aws-client (needed for internal PyPi)](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html)
* [python3.12](https://www.python.org/downloads/)
* [poetry](https://python-poetry.org/)
* [CodeArtifact (needed for installing dependencies)](https://github.com/celonis/python-core/blob/main/docs/CODE_ARTIFACT.md#local-development)

**Pyenv (recommended)**:
Follow the [pyenv](https://github.com/pyenv/pyenv#installation) installation guide to set up your local
development environment to manage different versions of python.

Then install the python 3.12 and make it available to your local pig-compability-wrapper repository:
```bash
# install required python versions (versions might not be latest!)
$ pyenv install 3.12.1

$ cd <path-to-repository>/pig-compability-wrapper
# generate a local .python-version file
$ pyenv local 3.12.1
```

### Running locally

- Installing Dependencies (requires ability to install artifacts from CodeArtifact)
  ```bash
  aws sso login --profile pypi
  export POETRY_HTTP_BASIC_CELOAI_USERNAME=aws
  export POETRY_HTTP_BASIC_CELOAI_PASSWORD=`aws codeartifact get-authorization-token --domain celonis-prod --domain-owner 867928363078 --region eu-central-1 --query authorizationToken --output text --profile=pypi`
  poetry install
  ```
  > __Note:__ The POETRY_HTTP_BASIC_CELOAI_PASSWORD is only valid for a few hours and needs to be refreshed once it expires.

- Start the Proxy
  ```bash
  poetry run python_core_proxy
  ```

- Start a local RabbitMQ
  ```bash
  docker run --rm -it -p 15672:15672 -p 5672:5672 rabbitmq:3-management
  ```

- Start the service itself
  - via Docker
    ```bash
    poetry run python_core_docker run --type=service --target=develop --python-version=3.12 --build
    ```
  - via Python
    ```bash
    poetry run python -m app.main
    ```
    - via IntelliJ
      - Change the working directory in the run configurations to the root directory (<path-to-repository>/pig-compability-wrapper)
      - Click the play or debug button within app/main.py


- Checkout the API documentation via http://localhost:9080/api/public/docs
- Download the OpenAPI spec via: http://localhost:9080/api/public/openapi.json

### Making requests
In order to make a request, set these authentication headers:

```
Authorization: Bearer <JWT_TOKEN>
```
```
x-celonis-service: <JWT_TOKEN>
```
> __Note:__ The <JWT_TOKEN> can be generated by using the JWT secret and the HS512 algorithm on [jwt.io](https://jwt.io/)

Sending a request should result in `"This is a test"` being returned
```bash
curl --header "x-celonis-service: <JWT_TOKEN>" --header "Authorization: Bearer <JWT_TOKEN>" http://0.0.0.0:9080/pig-compability-wrapper/api/feature_a
```

### Tests
The tests for python core services are divided into unit, integration, and e2e tests.

To run all tests locally, simply execute:
```bash
poetry run pytest -n=auto tests
```

#### Unit Tests
Unit tests test a single unit of source code and do not require any network connection, file system, or database to be executed.
All required external components have to be mocked using e.g. `unittest.mock`.

#### Integration Tests
Integration tests combine individual software modules and test them as a group.
For Python Core services this e.g. means that unlike a unit test where router and service are tested separately, a full app is started and tested.
Like unit tests, they do not require any network connection, file system, or database to be executed and rely on mocks instead.

#### E2E Tests
The last type of tests used by Python Core services are E2E tests.
These test the full functionality including http requests, database connections, and so on.

Therefore, they need a full development setup to be executed.
For Python Core services this can be achieved by starting the `python_core_proxy` to connect to all required services.
They also need the following envs set to connect to the right team:
- `CELONIS_AUTHORIZATION`: Authorization header used for requests (e.g. `AppKey <APP_KEY>`). Only AppKeys are supported!
- `CELONIS_TEAM_DOMAIN`: Domain of team to be used (e.g. `applied-ml`).
- `SECURITY_JWT_TOKEN`: Same token as used by `python_core_proxy`.

You can then run the tests using:
```bash
poetry run pytest -n=auto --disable-vcr tests/e2e
```

We rely on [PyVCR](https://pytest-vcr.readthedocs.io/en/latest/) which records all HTTP requests in cassettes that are then replayed during test execution.
This allows to execute e2e tests without having a development environment running (e.g. in your CI environment).
To run e2e tests using the cassettes simply remove the `--disable-vcr` flag:
```bash
poetry run pytest -n=auto tests/e2e
```

If you add a new test or change an existing test you have to record the cassette again to reflect this change.
This can be achieved by running:
```bash
poetry run pytest -n=auto --vcr-record=all tests/e2e/path/to/your/test
```

### Internal client generation
The template allows to easily call endpoints of other EMS services using an internal client.
You can add other required endpoints to your service:

1. Create new `yaml` file in the `resources` folder of your app (or use existing ones): `open-api-<service-name>.yaml`
2. Generate clients by running:
```bash
poetry run generate-clients --input_folder=./resources/services --output_folder=./app/services
```

### Java client generation
You can also generate a java internal client for your service based on the openapi.json file.
The generated client can then be used by java EMS services to call your service.
Simply run the `publish-java-internal-client` Github action which will generate the java client and publish it to the github maven repository.

You can also generate the client locally for testing purposes by running:
```
poetry run openapi_generator java pig-compability-wrapper ./openapi.json \
            --version=$(grep ^version pyproject.toml | cut -d '"' -f 2)-SNAPSHOT \
            --description="<Service Description>" \
            --output-path ./ \
            --package
```

### Features and Configuration
The service already comes with a client for the features and configuration framework which can be used for backend feature flags.
To make use of the feature and configuration system please look at their [documentation](https://www.celonis.dev/docs/default/component/backend/feature-and-configuration-system/feature-and-configuration-system/).

#### Troubleshooting
There are several common issues that might occur during the java client generation based on an openapi spec generated by fastapi:

- `TypeError: Schema: {} not supported!`: This error often occurs if no `response_model` is set or if an endpoint with no return value does not specify `status_code=204`.
